# RAG Document Assistant

A local PDF question-answering application with a manual retrieval-augmented
generation (RAG) pipeline. Upload a PDF, ask questions, and inspect retrieved
source excerpts alongside answers generated by Ollama's `llama3.2` model.

## Features

- PDF upload with validation and indexed chunk count.
- One active document, replaced after a new upload indexes successfully.
- Answers with source filenames, PDF page numbers, and expandable excerpts.
- Responsive React interface with loading states and error messages.
- Local embeddings, in-memory vector storage, and local LLM generation.

## Architecture and technology stack

```text
React / Vite
    |
    v
FastAPI (Pydantic request validation)
    |
    +-- PDF -> PyPDF -> overlapping chunks
    |                  -> SentenceTransformer embeddings -> ChromaDB
    |
    +-- Question -> embedding -> similarity retrieval from ChromaDB
                                -> context -> Ollama / Llama 3.2
                                                |
                                                v
                                         Answer + Sources
```

The backend uses Python, FastAPI, Pydantic, PyPDF, sentence-transformers,
ChromaDB, and the Ollama Python client. The frontend uses React, Vite, and plain
CSS. API handling lives in `backend/main.py`; PDF processing, indexing, retrieval,
and generation live in `backend/rag.py`.

The workflow extracts text page by page, creates 500-character chunks with
100-character overlap within each page, and embeds them with `all-MiniLM-L6-v2`.
A question is embedded with the same model; up to four relevant chunks become
the context for `llama3.2`. The prompt requires context-only answers and the
fallback `I don't know based on the document.` when information is missing.

## Backend setup

Prerequisites: Python (the current environment uses 3.13), Node.js 20.19+ or
22.12+, npm, and locally installed Ollama. These commands use Windows PowerShell
from the project root.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
ollama pull llama3.2
```

The requirements record the current environment's direct package versions.
Reuse an existing working `.venv` if present. Start Ollama through its desktop
application, or run `ollama serve` in another terminal if it is not already
running. The initial embedding-model load downloads `all-MiniLM-L6-v2`;
subsequent runs can use the local cache. No cloud LLM API key is required.

Run FastAPI with one backend worker:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

Interactive API documentation: http://127.0.0.1:8000/docs.

## Frontend setup

In a second terminal:

```powershell
cd frontend
npm ci
npm run dev
```

Open http://127.0.0.1:5173. The frontend defaults to the backend at
`http://127.0.0.1:8000`; set `VITE_API_URL` before starting Vite to override it.
FastAPI permits local frontend origins on port 5173. Vite environment variables
are browser-visible and must never contain secrets.

Create a production build with `npm run build`.

## API endpoints

| Endpoint | Request | Response |
| --- | --- | --- |
| `POST /upload` | Multipart form with a PDF in the `file` field | `filename`, `chunks_stored`, `message` |
| `POST /ask` | JSON: `{"question":"What does this document describe?"}` | `answer` and `sources` |
| `GET /` | None | API health message |

Each source contains `filename`, a 1-based `page`, and retrieved `text`.
Non-PDF uploads return 415; empty, unreadable, or textless PDFs return 422.
Empty questions return 422; questions without an indexed document return 400.
Ollama connection/model failures return 503/502.

## Current limitations

- **One active PDF per backend process.** Successful uploads replace the old
  index; failed uploads preserve it. Documents are not combined.
- Chroma is in memory. Upload again after restarting or reloading the backend.
  Uploaded PDFs stay in `backend/documents/` under unique names but are not
  automatically reindexed.
- Scanned/image-only PDFs require OCR, which is **not implemented**.
- Sources are retrieved context, not verified citations for each sentence.
  Model answers can be imperfect; inspect excerpts when checking an answer.
- The application is intended for local development and has no authentication.

## Tests

From the project root:

```powershell
.\.venv\Scripts\python.exe -m unittest backend.test_workflow -v
```

The default tests cover validation, index replacement, sources, and errors with
real embeddings/Chroma and mocked Ollama. Set `RAG_LIVE_TESTS=1` to enable the
live backend test. It requires the two local PDFs named in
`backend/test_workflow.py`; these PDFs are intentionally not included in Git.
Existing learning scripts are preserved and some also require local PDFs or Ollama.

From `frontend/`, run `npm run test:e2e` for browser checks using installed
Microsoft Edge in headless mode. Set `RAG_BROWSER_LIVE=1` to include the real
backend/Ollama test; this requires the sample PDF named in
`frontend/tests/app.spec.js` and a running backend. Live tests replace the active
document. Tests start Vite on port 5173; set `PLAYWRIGHT_REUSE_SERVER=1` to use an
already running frontend instead.

## Repository hygiene

Commit source files and the npm lockfile. Local PDFs, uploaded documents,
environment files, virtual environments, dependencies, caches, test output, and
build artifacts are ignored. A sanitized `.env.example` may be committed if
needed. Local PDFs are preserved and must not be force-added to Git.
